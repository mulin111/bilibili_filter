# B站推荐流高频投稿屏蔽

一个运行在浏览器油猴（Tampermonkey / Violentmonkey）里的 B 站首页 / 视频页推荐流过滤器。

默认规则：**最近 24 小时内投稿 ≥ 5 个的 UP，在首页和视频页推荐卡片里显示为占位提示**。

本地判断和隐藏；命中屏蔽后可按设置向 B 站提交「不感兴趣」反馈，让推荐系统收到信号。

## 1.2.1 新增

- 规则页新增「白名单关键词」：命中标题 / UP 名后直接显示卡片，优先于高频投稿、黑名单、关键词和低播放规则。
- 白名单关键词支持普通包含或正则、匹配标题 / UP 名，默认关闭。

## 1.2.0 新增

- 命中屏蔽后，默认等待 5 秒自动向 B 站提交「不想看此UP主」反馈；可在「显示 → 不感兴趣反馈」关闭或改为所有规则。
- 占位卡增加「不感兴趣」按钮，可手动提交；同一 UP / 视频 24 小时内最多自动提交一次。
- 「显示一次」会取消尚未提交的自动反馈；「不再屏蔽」会取消自动反馈，并尝试撤销已提交的反馈。
- 反馈需要登录 B 站；未登录或接口失败时只影响反馈，不影响本地隐藏。
- 缓存记录视频 aid，高频命中反馈时通常不需要额外请求视频详情。

## 1.1.1 修复

- 可见卡片每次页面加载/刷新都会后台刷新一次；同一页面内超过 1 小时也会刷新。
- 缓存结果先显示，不等待刷新；这样既不会等，也不容易被旧缓存挡住。
- 日志增加「缓存命中」「已关注跳过」「白名单命中」原因，方便定位为什么没屏蔽。

## 1.1.0 更新

- 请求队列改为每批最多 2 个、批间隔约 0.8 秒；20 个请求后约 1.2 秒。
- 用 IntersectionObserver / MutationObserver 替代 2 秒全量扫描，新增 5 秒安全扫描。
- 总投稿数不足阈值 24 小时；部分数据 2 小时；其余每次页面加载/1 小时后台刷新。
- 日志显示窗口内命中数；悬浮按钮旁显示「正在检查 N 个 UP」。
- 视频页悬浮按钮移到右下角，避开点赞栏；面板增加保守模式。

## 功能

- 首页推荐卡片：识别 UP 的 UID，读取最近投稿，命中阈值后屏蔽该 UP 的所有卡片。
- 视频页右侧「相关推荐」和页面内推荐卡片：同一套规则；不处理播放器、UP 头部和「接下来播放」。
- 默认跳过已关注 UP：
  - 首页使用卡片上的「已关注」标识。
  - 视频页卡片没有该标识时，若 UP 已命中高频规则，会额外调用一次 B 站关系接口判断关注状态；可在面板关闭。
- 占位提示：显示 UP 名、命中原因，可「不感兴趣」「显示一次」或「不再屏蔽」。
- 规则可配置：
  - 高频投稿：阈值 / 时间窗口 / 近期任意窗口 / 回溯天数 / 排除直播回放 / 关注豁免。
  - 关键词：黑名单关键词 + 白名单关键词；标题或 UP 名，普通包含或正则。白名单关键词命中后优先显示。
  - 指定 UP：白名单 / 黑名单 UID，支持从占位卡一键添加。
  - 低播放：按卡片显示值近似判断（支持「万 / 亿」）。
- 面板 + 油猴菜单；完整规则支持 JSON 编辑、校验、导入/导出、恢复默认。
- 不感兴趣反馈：默认只对高频投稿命中自动提交「不想看此UP主」；可改为所有规则或关闭；也可在占位卡手动点。
- 请求限速、缓存、失败放行；接口被限流时自动暂停并切到保守模式。
- 观察器驱动：卡片进入视口立即检查，不再每 2 秒全量扫描。
- 悬浮按钮旁显示「正在检查 N 个 UP」进度；日志显示窗口内命中数量。

## 安装

### 1. 安装油猴管理器

推荐：

- Chrome / Edge：[Tampermonkey](https://www.tampermonkey.net/)
- Firefox：[Tampermonkey](https://www.tampermonkey.net/) 或 [Violentmonkey](https://violentmonkey.github.io/)

> Greasemonkey 4 的跨域请求接口与 Tampermonkey 不同，未做专门适配。

### 2. 安装脚本

方式一：把 `bili-feed-filter.user.js` 拖进浏览器窗口，Tampermonkey 会打开安装页。

方式二：打开 Tampermonkey 面板 → 「添加新脚本」→ 清空编辑器 → 粘贴 `bili-feed-filter.user.js` 的全部内容 → `Ctrl+S` 保存。

首次运行时，Tampermonkey 可能询问是否允许访问以下域名，请允许：

- `app.bilibili.com`（读取 UP 公开投稿列表）
- `api.bilibili.com`（网页接口兜底、视频页关注状态检查）

### 3. 更新旧版本

- 用新的 `bili-feed-filter.user.js` 覆盖 Tampermonkey 里的旧脚本，保存后刷新 B 站。
- 设置和缓存的存储 key 没变，通常可以直接沿用；「缓存 / 日志」里确认版本是 1.2.1。
- 只刷新 B 站页面而没更新脚本，仍然会运行旧版本。

### 4. 使用

打开 `https://www.bilibili.com/` 首页，或任意普通视频页（`/video/BV...`）：

- 首页左下角、视频页右下角会出现一个蓝色「屏」按钮（视频页避开点赞栏），点击打开设置面板。
- 不想看到按钮：面板「显示」里取消「显示悬浮按钮」，之后通过油猴菜单「打开设置面板」进入。
- 默认已经开启高频投稿规则，不需要额外配置。

首次打开时只检查进入视口的卡片；首屏通常 2–5 秒内开始出现占位提示，之后使用缓存基本即时。滚动时新卡片会通过观察器立即入队。

| 项目 | 默认值 |

| 高频投稿 | 最近 24 小时 ≥ 5 个公开投稿 |
| 统计方式 | 当前窗口 |
| 排除直播回放 | 开启 |
| 跳过已关注 UP | 开启 |
| 视频页关系接口判断关注 | 开启 |
| 屏蔽样式 | 占位提示 |
| 生效页面 | 首页 + 视频页相关推荐 |

## 规则配置

### 支持的四类规则

当前版本只实现以下四类：

| type | 作用 | 数据来源 |
|---|---|---|
| `up-mass-upload` | 高频投稿 | 卡片 UID + B 站公开投稿列表接口 |
| `keyword` | 标题 / UP 名关键词（block / allow） | 卡片 DOM |
| `uid-list` | 指定 UP 白名单 / 黑名单 | 卡片 UID / UP 名 |
| `play-count` | 低播放 | 卡片显示的播放数（近似） |

分区、精确播放数、视频时长、发布时间等依赖视频详情元数据的规则，计划在第二版加入；当前版本在 JSON 里写这些 `type` 会校验失败。

### 配置方式

面板「规则」页提供常用规则的简单表单：

- 高频投稿阈值 / 窗口 / 回溯 / 排除直播回放 / 关注豁免
- 白名单关键词 / 关键词列表、匹配标题 / UP 名、正则开关
- 白名单 / 黑名单 UID
- 低播放最小 / 最大播放数

更复杂的组合使用「编辑完整 JSON」。JSON 支持：

- 校验并保存
- 格式化
- 导出 `bff-rules.json`
- 导入文件（导入后需要点「校验并保存」）

项目里的 `rules.example.json` 是默认模板。

### JSON 结构

```json
{
  "version": 1,
  "rules": [
    {
      "id": "mass-upload",
      "type": "up-mass-upload",
      "enabled": true,
      "action": "block",
      "scope": ["home", "video"],
      "config": {
        "threshold": 5,
        "windowHours": 24,
        "rolling": false,
        "lookbackDays": 7,
        "excludeLiveReplay": true,
        "skipFollowed": true,
        "videoFollowedCheck": true
      }
    }
  ]
}
```

字段说明：

- `id`：唯一字符串，用于日志和面板定位。
- `type`：`up-mass-upload` / `keyword` / `uid-list` / `play-count`。
- `enabled`：是否启用。
- `action`：`block`（屏蔽）或 `allow`（放行）；默认 `block`。`allow` 规则先执行，优先级高于所有 `block` 规则。
- `scope`：`home` / `video`，默认两者都生效。
- `config`：按类型不同。
- `reason`（可选）：自定义屏蔽原因，最多 200 字；会显示在占位卡和日志里。

### 高频投稿 `up-mass-upload`

```json
{
  "id": "mass-upload",
  "type": "up-mass-upload",
  "enabled": true,
  "action": "block",
  "scope": ["home", "video"],
  "config": {
    "threshold": 5,
    "windowHours": 24,
    "rolling": false,
    "lookbackDays": 7,
    "excludeLiveReplay": true,
    "skipFollowed": true,
    "videoFollowedCheck": true
  }
}
```

- `threshold`：2–20。
- `windowHours`：1–168。
- `rolling: false`：只统计「当前时间往前 `windowHours` 小时」。
- `rolling: true`：统计「最近 `lookbackDays` 天内任意一个 `windowHours` 小时窗口」的最大投稿数，用来抓几天前发生过的集中爆发。
- `lookbackDays`：1–7。
- `excludeLiveReplay`：排除直播回放，避免误伤主播。
- `skipFollowed`：跳过已关注 UP。
- `videoFollowedCheck`：视频页卡片没有「已关注」标识时，是否调用 B 站关系接口判断关注。关闭可减少一次请求，但视频页可能屏蔽已关注 UP。

### 关键词 `keyword`

```json
{
  "id": "keywords",
  "type": "keyword",
  "enabled": true,
  "action": "block",
  "scope": ["home", "video"],
  "config": {
    "keywords": ["营销号", "标题党"],
    "matchTitle": true,
    "matchUpName": false,
    "regex": false
  }
}
```

- `keywords`：最多 100 个，每个不超过 200 字。
- `matchTitle` / `matchUpName`：至少开启一个。
- `regex: false`：普通包含匹配，英文不区分大小写。
- `regex: true`：每个关键词都按正则表达式处理；非法正则会校验失败。
- `action` 可以是 `allow`，例如放行标题里带「官方」的内容。白名单关键词建议使用独立规则：

```json
{
  "id": "keywords-allow",
  "type": "keyword",
  "enabled": true,
  "action": "allow",
  "scope": ["home", "video"],
  "config": {
    "keywords": ["官方", "发布会"],
    "matchTitle": true,
    "matchUpName": false,
    "regex": false
  }
}
```

白名单关键词会在所有 `block` 规则之前匹配，命中后直接显示卡片，包括原本会被高频投稿、黑名单、关键词或低播放规则屏蔽的卡片。

### 指定 UP `uid-list`

```json
{
  "id": "blacklist",
  "type": "uid-list",
  "enabled": true,
  "action": "block",
  "scope": ["home", "video"],
  "config": {
    "uids": ["123456"],
    "names": []
  }
}
```

- `uids`：UID 字符串数组；建议优先使用 UID。
- `names`：UP 名精确匹配（英文不区分大小写），可选；改名或重名会失效。
- `action: "allow"` 是白名单，默认的 `whitelist` 规则就是这种；`action: "block"` 是黑名单。
- 白名单优先于所有屏蔽规则。占位卡上的「不再屏蔽」会自动把 UID 加入 `whitelist`。

### 低播放 `play-count`

```json
{
  "id": "low-play",
  "type": "play-count",
  "enabled": true,
  "action": "block",
  "scope": ["home"],
  "config": {
    "min": 0,
    "max": 1000
  }
}
```

- `min` / `max`：播放数区间，包含边界。
- 使用卡片上显示的播放数，例如 `800`、`2.8万`、`1.2亿`；不是接口精确值。
- 卡片没有播放数、或第一位显示的是 `01:23` 这类 VT / 时长指标时视为不匹配，不会误屏蔽。
- 部分开启 VT 的卡片可能不显示播放数而显示其它指标，此时低播放规则可能不准确。

### 执行顺序

1. `allow` 规则先执行；命中直接显示卡片，不再查接口。
2. 再执行不依赖接口的 `block` 规则：关键词、UID、低播放。
3. 最后执行高频投稿规则（需要查询 UP 投稿）。
4. 某条规则数据缺失或接口失败时只跳过该条；所有规则都不命中/无法判断时，卡片保持显示。

这样在关键词或 UID 已经命中时不会浪费投稿接口请求。

## 数据来源与请求策略

### 高频投稿

使用 B 站 App 的公开投稿列表接口：

```text
https://app.bilibili.com/x/v2/space/archive
```

- 一次最多 20 条；按发布时间倒序。
- 默认只请求 1 页，足够判断阈值 ≤ 20 的当前窗口。
- 开启「近期任意窗口」时按需请求最多 3 页（60 条）。
- 匿名请求，不带 Cookie，不需要登录。

如果 App 接口不可用（签名/版本变更等），会尝试网页空间接口：

```text
https://api.bilibili.com/x/space/arc/search
```

网页接口风控更严格，可能返回 412 / -799；失败时不会影响卡片显示。

### 视频页关注状态

首页的「已关注」标识可以直接从卡片读取，不需要请求。

视频页卡片没有该标识；只有在以下条件同时满足时才请求一次关系接口：

- 高频投稿规则已经判定该 UP 命中；
- 开启了「跳过已关注 UP」；
- 开启了「视频页用关系接口判断关注」；
- 该 UID 24 小时内没有关注状态缓存。

```text
https://api.bilibili.com/x/relation?fid={uid}
```

这个请求会带当前 B 站登录 Cookie，仅用于决定是否豁免；未登录时返回 `-101`，按未关注处理。

### 不感兴趣反馈

命中屏蔽后，脚本调用 B 站网页的反馈接口：

```text
https://api.bilibili.com/x/web-interface/feedback/dislike
```

- 默认理由 `reason_id=4`（不想看此 UP 主），可改为 `1`（内容不感兴趣）。
- 只对高频投稿命中自动反馈；可在面板改为所有规则命中或关闭。
- 提交前等待 5 秒，给「显示一次 / 不再屏蔽」留出取消时间。
- 同一 UP（不想看此UP主）或同一视频（内容不感兴趣）24 小时内最多成功提交一次；失败后 30 分钟内不自动重试。
- 每次页面加载最多自动反馈 10 次；超过后仍可在占位卡手动点。
- 请求带当前 B 站登录 Cookie 和 `bili_jct` CSRF token，只发送给 `api.bilibili.com`。
- 未登录、接口失败或被限流时，本地隐藏仍然生效，不会因为反馈失败而放行卡片。
- 「不再屏蔽」会尝试调用 `/feedback/dislike/cancel` 撤销已提交的反馈。
- 自动反馈会以你的账号提交，属于真实的账号操作；脚本已做 5 秒延迟、1 并发限速、每个对象 24 小时一次、每次页面最多 10 个，但仍请自行评估账号风控风险。

### 限速与缓存

- App 投稿队列默认每批最多 2 个请求，批间隔约 0.8 秒；20 个请求后间隔约 1.2 秒，不再无限拉长。
- 只检查进入视口附近的卡片；用 IntersectionObserver 在卡片进入视口时立即处理，5 秒一次安全扫描兜底。
- 缓存结果先显示；可见 UP 每次页面加载/刷新后台刷新一次，同一页面内超过 1 小时再刷新；总投稿数小于阈值的 UP 24 小时刷新；部分数据 2 小时刷新。
- 关注状态缓存 24 小时。
- 反馈队列 1 并发，约 1–1.4 秒一条；反馈接口限流时暂停 10 分钟。
- 412 / -799 / -352 / -509 自动暂停 10 分钟，并切换到保守模式（1 并发 1.5 秒）；面板可手动切回。
- 网络错误重试一次；仍失败则 30 分钟后重试。
- **投稿频率接口失败/限流一律不屏蔽（fail-open）**，不会因为接口挂了把所有卡片隐藏。
- 视频页关注状态接口失败时，由于高频判定已经完成，会按未关注处理并屏蔽；如果不希望这样，关闭「视频页关系接口判断关注」或把 UP 加白名单。

面板「缓存 / 日志」可以查看缓存数量、关注缓存、反馈记录、最近检查时间、调试日志（含每个 UP 的窗口内命中数），也可以清空缓存、清空反馈记录或重新检查当前页。清空反馈记录只删除本地记录，不会撤销已提交给 B 站的反馈；撤销请用占位卡「不再屏蔽」。悬浮按钮旁会显示「正在检查 N 个 UP」。

## 隐私

- 所有判断和缓存都在本机。
- 没有自建服务器，不上传任何浏览记录或账号信息。
- 投稿频率查询是匿名请求，只发送 UP 的 UID。
- 视频页关注状态查询和「不感兴趣」反馈会带 B 站登录 Cookie，但只请求 B 站自己的 `api.bilibili.com`，不会发给第三方。
- 反馈是可选功能：默认只对高频投稿命中提交「不想看此UP主」，可在面板关闭；提交前有 5 秒取消时间。
- 不修改 B 站页面以外的内容。

## 常见问题

### 为什么某个高频 UP 没有被屏蔽？

按可能性排查：

1. 该 UP 是你已关注的，触发了关注豁免。
2. 卡片还没进入视口，或刚进入视口，请求还在队列里；自动反馈还要再等 5 秒。
3. 缓存结果先显示；页面加载/1 小时后会后台刷新。总投稿数不足阈值的 UP 24 小时刷新。
4. 日志里出现「已关注，跳过」说明是关注豁免；出现「缓存命中」说明还没到刷新时间。
5. 投稿接口被限流，脚本暂停了检查；看「缓存 / 日志」。
6. UP 最近投稿里直播回放被排除后，没有达到阈值。
7. 卡片的播放数/标题/UID 结构和预期不同，脚本没提取到；开调试日志看。
8. 你使用的是视频页的「接下来播放」卡片——这张卡默认不处理，避免干扰自动连播。

### 为什么没有提交「不感兴趣」反馈？

1. 没有登录 B 站，或 `bili_jct` Cookie 已失效。
2. 设置了「不自动」；此时只能点占位卡上的「不感兴趣」。
3. 5 秒等待期内点过「显示一次」或「不再屏蔽」，自动反馈会被取消。
4. 该 UP 24 小时内已经成功反馈过；同一 UP 不会重复提交。
5. 反馈接口被限流（日志有 WARN），会暂停 10 分钟。
6. 没找到视频 aid（接口异常或卡片结构变化）；日志会写「未找到视频 aid」。

### 为什么已关注的 UP 也被屏蔽了？

- 首页卡片的「已关注」标识没有渲染出来，或 B 站改版导致识别失败。
- 视频页卡片关系接口失败、未登录，或 24 小时缓存过期前关注状态有变化。

直接点占位卡上的「不再屏蔽」加入白名单即可。

### 为什么卡片会先显示几秒再变成占位？

脚本只检查进入视口的卡片，默认每批最多 2 个请求、批间隔约 0.8 秒；20 个请求后约 1.2 秒。首屏需要逐张检查，通常 2–5 秒内开始出现占位；之后命中缓存会立即生效。

### 会不会导致 B 站账号被风控？

投稿频率查询是匿名接口，不携带账号 Cookie，只使用 UID；请求频率做了限制。网页兜底接口和关系接口使用当前网络/IP，仍可能被限流，但脚本会暂停并自动切换到保守模式。面板里也可以手动开启保守模式。

「不感兴趣」反馈会以你的账号真实提交，属于账号操作；脚本已限制为 1 并发、5 秒延迟、每个对象 24 小时一次、每次页面最多 10 个，但仍可能触发 B 站风控。若不希望自动提交，把「自动反馈」设为「不自动」，只手动点。

### 这能改变 B 站的推荐算法吗？

会，但取决于反馈设置。默认在命中高频投稿后 5 秒提交「不想看此UP主」，B 站推荐系统会收到负反馈；如果只想本地隐藏，把「自动反馈」设为「不自动」即可。手动反馈按钮仍然可用。

### 支持手机端 / 搜索页 / 分区页吗？

当前只支持桌面版：

- `https://www.bilibili.com/` 首页
- `https://www.bilibili.com/video/...` 普通视频页的右侧相关推荐与页面内推荐

不支持 `m.bilibili.com`、番剧、直播、搜索、分区、个人空间等页面。

### 为什么不用 uBlock Origin 规则？

uBlock 只能按 URL/元素选择器静态拦截，无法判断「这个 UP 最近 24 小时投了几个视频」。这个规则需要读取投稿时间并做计算。

### 怎么卸载？

- 在 Tampermonkey 里删除脚本。
- 如需清理缓存：面板「缓存 / 日志」→「清空 UP 缓存」「清空关注缓存」「清空反馈记录」，或清除该站点的 localStorage / 油猴脚本存储。清空反馈记录不会撤销已经提交给 B 站的反馈。

## 开发与测试

文件结构：

```text
bili-feed-filter/
├── bili-feed-filter.user.js   # 单文件油猴脚本
├── rules.example.json          # 默认规则模板
├── README.md
└── test/
    └── rule.test.js            # Node 内置测试
```

脚本顶部的纯函数会通过 `module.exports` 暴露给测试；浏览器里不会执行 Node 相关代码。

运行测试（需要 Node 18+）：

```bash
node --test test/rule.test.js
```

测试覆盖：

- MD5 与 B 站 App 接口签名
- 播放数「万 / 亿」解析
- UID / BV 号提取
- 当前窗口 / 滚动窗口计数
- 高频投稿判定与直播回放排除
- 规则校验（重复 ID、非法正则、阈值范围等）
- 白名单 UID / 白名单关键词优先、关键词、指定 UP、低播放
- 页面 scope、禁用规则

手动测试建议：

1. 安装脚本，打开首页。
2. 打开面板「缓存 / 日志」，确认能看到「已检查」日志。
3. 找一张明显高频的 UP 卡片，确认变成占位提示。
4. 点「显示一次」，确认该 UP 的卡片恢复；刷新后重新屏蔽。
5. 点「不再屏蔽」，确认加入白名单并保持显示。
6. 在「白名单关键词」填「官方」，保存，确认标题含「官方」的卡片恢复显示。
7. 打开视频页，确认右侧相关推荐生效、「接下来播放」不受影响。
8. 在开发者工具里把 `app.bilibili.com` 请求改为失败，确认卡片保持显示而不是被误屏蔽。
